# h5 step H5-4: training loop

The training loop for the ray decoders, with validation over the decoding grid, checkpoints and resume.
Branch `h5`. Nothing in `src/`, `phd_work/`, `csgbox` or `dexelize` was changed. No dependency was added
(PyYAML is already in the ConvONet venv). **The pilot runs (P1 and later) have not been started.** The
measurements below are short benchmark runs in a scratch directory, not training results.

## Files

- `h5/train.py`: the loop. `run(cfg, resume, device)` and the CLI
  `.venv/bin/python h5/train.py h5/configs/T.yaml [--resume] [--max-it N] [--out-dir DIR]`.
- `h5/configs/default.yaml`: the shared defaults. `h5/configs/{hits_8, hits_8_plane, occfrac_128, tsdf_128,
  binary_128}.yaml`: the target and its `out_dir`. Unknown keys are errors.
- `h5/eval_rays.py` (changed): decoding grids, cached validation data, and one network pass per shape for
  the whole grid (see below).
- `h5/tests/test_h5_4.py`: the smoke tests (GPU).

## Data and determinism

Global sample `g` of a run is shape `perm_epoch[g mod n]` (permutation of the training shapes per epoch,
`Generator(SeedSequence([seed, 1, epoch]))`), and its rays and points come from
`Generator(SeedSequence([seed, 2, g]))`. Iteration `i` uses samples `i B … i B + B − 1`. A resumed run
therefore draws the same batches as an uninterrupted run, and the number of workers does not change the data.
The DataLoader is a map-style dataset with a `range` sampler.

Training is **not bit-deterministic on the GPU**: the backward of `grid_sample` has no deterministic CUDA
kernel. Evaluation is: `run_decoder` runs its forward under `torch.use_deterministic_algorithms(True)`
(context `deterministic_kernels`). Without it, two encodes of the same shape differed by up to 0.067 on plane
values of size ~110 (scatter order), which flipped threshold decisions and moved F1 by up to 2e-4.

## Files of a run

| file | content |
|---|---|
| `config.json` | the merged configuration |
| `train_subset.json` | the chosen training shapes (if `train_subset` or `eval_on_train`) |
| `log.jsonl` | every `log_every` iterations: `iteration`, `loss`, `parts` (`L_t`, `L_mask` for hits; `informative`, `other`, `entropy_floor`, `excess` for dense), `s_per_it` (training time including the data wait, validation excluded), `peak_gib` |
| `val.jsonl` | every validation: `iteration`, `selected` (the setting with the best F1 at delta 0.002), `selected_f1`, `f1` (one value per setting), `settings` (the full `aggregate` summary of every setting), `val_seconds` |
| `model_last.pt` | model, optimizer, iteration, best F1 and iteration, CPU and CUDA RNG states, config. Written at every validation (atomically); used by `--resume` |
| `model_best.pt` | the model with the best validation F1 (over the grid), with its decoding setting |
| `model_it{N}.pt` | model weights, the selected setting and its summary, at each validation |
| `model_it{N}.json` | the selected setting, its F1 and its summary, next to `model_it{N}.pt` |

The checkpoints load with `h5/scripts/eval_rays.py --checkpoint` (keys `target`, `state_dict`).

## Decoding grids

One network pass per shape serves all settings (`grid_summaries`):

| target | settings |
|---|---|
| `hits_8`, `hits_16`, `hits_8_plane` | mask threshold 0.3, 0.4, 0.5, 0.6, 0.7 |
| `occfrac_128` | `occ_snap` 1e-3, 1e-2, 0.03, 0.1 (the threshold 0.5 is not used; the literal rule is not in the grid) |
| `binary_128` | threshold 0.3, 0.4, 0.5, 0.6, 0.7 |
| `tsdf_128` | none (one setting) |

The GT of the validation shapes (restricted to their fixed rays, and the full GT for `eval_on_train`) is
cached in memory by `prepare_fixed` / `prepare_all` after the first validation, so later validations do not
call `gt_hits`. The cache is per process.

## Timing (real data, 4 workers, n_rays 512)

Benchmark runs of 300 iterations (batch 32, GPU RTX 4070, fp32), the default validation (200 shapes × 4096
rays, all settings). Scratch directory; not the pilot. `s_per_it` is the mean over each window of 50
iterations, including the data wait and excluding validation.

| target | s/it (iterations 50–300) | peak GPU memory | first validation (200 shapes, cold GT cache) | cached validation (same process) |
|---|---|---|---|---|
| hits_8 | 0.214–0.226 | 4.3 GiB | 29.3 s (benchmark run), 30.7 s (fresh process) | **9.0 s** |
| occfrac_128 | 0.204–0.227 | 4.2 GiB | 87.0 s (benchmark run) | **65.6 s** |

Notes on the validation times. The GT of the 200 shapes costs about 21 s, paid once per process
(hits_8: 30.7 s cold, 9.0 s cached). The occfrac time is the decoding and scoring of four settings for an
early checkpoint (300 iterations), whose outputs have many partial cells, so many hits are decoded. A later
checkpoint will decode to far fewer hits, and the time will be lower. This was not measured.

## Choices (not obvious from the spec)

1. **Validation metric and selection.** The selection is the best F1 at delta 0.002 over the grid; the
   validation runs at every `val_every` and at `max_it`. `model_best.pt` is written only when the F1 improves
   (NaN never improves).
2. **Dense loss.** dense_loss (0.5 mean over informative + 0.5 mean over the other cells) is the 50 % rule. The (1-f)/f weights of H5-1b are an equivalent formulation and are not applied separately. The excess is logged for occfrac.
3. **Iteration and samples.** `iteration` counts the optimizer steps. Each step uses one batch of `batch_size`
   consecutive global samples; the resume point is `iteration · batch_size`.
4. **Refusing to mix runs.** A new run into a directory that already has `log.jsonl` or `model_last.pt` is an
   error; use `--resume`.
5. **Checkpoint writes** are atomic (`tmp` then `rename`), so a crash during a save leaves the previous
   `model_last.pt` in place.
6. **RNG state** is saved with the checkpoint. The training itself draws no random numbers beyond the explicit
   seeds, so the RNG state does not change the batches.

## Limits

- Resume reproduces the batches and the optimizer state exactly, but not the GPU arithmetic (see test b).
- The validation cache is per process and keyed by split, index and `n_rays`. A changed `val_rays` builds a new
  entry.
- `eval_on_train` evaluates all rays of the subset, so it is slower and its F1 is not comparable with the
  4096-ray validation.
- `hits_16` is accepted by `train.py` but has no config file and no smoke test.

# h5 step H5-5a: point decoders and the ray protocol

Point decoders for the h5 training loop (`points_std`, `points_strong`) and the ray protocol that turns a
point decoder into ray hits, so that point decoders are validated and evaluated in the same ray space as the
ray decoders. Branch `h5`. Nothing in `src/`, `phd_work/`, `csgbox` or `dexelize` was changed. The decoder is
ConvONet's own `LocalDecoder` and the encoder is ConvONet's `LocalPoolPointnet` (as `H5RayModel`).

## Interfaces

### Data: `h5/data.py` (added)

- `POINT_TARGETS = ("points_std", "points_strong")`, `N_QUERY = 2048` (ConvONet `points_subsample`).
- `read_occupancy_points(path) -> (points float32, occ float32)`: the packed occupancies unpacked as ConvONet
  does (`np.unpackbits(...)[:P]`).
- `build_point_item(shape_dir, rng, target, n_points, noise, n_query=2048)`: the encoder input as in
  `build_item` (10000 points from `pointcloud.npz`, noise 0.001), and the query points:
  - `points_std`: 2048 uniform from `points.npz`;
  - `points_strong`: 1024 from `points.npz` and 1024 from `points_surface.npz`. That file holds 50 000 points at
    sigma 0.002 and 50 000 at sigma 0.01; the sample is uniform over the stored file, so both halves are used.
  - Items: `inputs` (10000, 3) float32, `query` (2048, 3) float32, `occ` (2048,) float32 in {0, 1},
    `from_surface` (2048,) bool (True for the surface draws).
- `PointShapeDataset(split, target, n_points, noise, seed, root)`: one item per shape, with the same per-item
  seeding as `RayShapeDataset`.

### Model: `h5/models.py` (added)

- `PointModel(target)`: `encoder` (as `H5RayModel`) and `decoder = LocalDecoder(dim=3, c_dim=32, hidden_size=32,
  sample_mode='bilinear', padding=0.1)`, ConvONet's `simple_local` with the `shapenet_3plane.yaml` settings
  (5 residual blocks, the `LocalDecoder` default). `decode(planes, query)` gives the logits (B, P);
  `forward(inputs, query)` gives `{"logits"}`. `kind = "points"`.
- `build_model(target, cfg)`: `PointModel` for the point targets, `H5RayModel` otherwise.
- Parameters: encoder 1 962 208, decoder 16 001.

### Loss: `h5/train.py` (point branch)

ConvONet's loss: `binary_cross_entropy_with_logits(logits, occ, reduction='none').sum(-1).mean()`, that is the
sum over the 2048 query points, averaged over the shapes of the batch. The log records `loss` only.

### Ray protocol: `h5/eval_points.py` (new)

- `ray_geometry(ray_axis, ray_index, n=128) -> (origins, dirs)`: the rays of the dexel grid, exactly
  `csgbox.grid.ray_grid` (origin with axis coordinate 0 and the cell centres on the other two axes; direction
  `e_axis`). Checked equal to `ray_grid` in test a.
- `ray_protocol(prob_fn, origins, dirs, isos, n=512, bisect=8, dtype, device) -> list[RayHits]` (one per iso,
  all rays in input order):
  1. `N` uniform samples per ray at `z_k = BOX_LO + (k + 1/2)(BOX_HI - BOX_LO)/N`, probabilities from `prob_fn`;
     the occupancy is `probability > iso`. The samples are computed once and shared by the isos.
  2. Every sign change between samples `k` and `k+1` is refined by `BISECT_STEPS = 8` bisection steps on
     `[z_k, z_{k+1}]`, keeping the side with the change. The hit is the midpoint of the final bracket. Enter means
     outside to inside.
  3. **Boundary hits (a rule of this protocol, the gate has none):** if the first sample is inside, an enter hit
     at `BOX_LO` is added before the first change; if the last sample is inside, an exit hit at `BOX_HI` is added
     after the last change. Without them a ray starting inside would begin with an exit.
  - Everything runs in torch, in ray chunks of 1024 rays, and the bisection in batches of 2^18 changes.
- `network_prob_fn(model, planes)`: the probability of a `PointModel` for one shape's plane features.

### Evaluation: `h5/eval_rays.py` (point branch)

- `decoding_grid("points_*") = [{"iso": 0.2}, {"iso": 0.5}]` (`POINT_ISO_GRID`).
- `point_hits(model, prep, isos, device)`: the encoder runs once per shape; the protocol with `N = 512`; the
  hits are split by axis with `subset_rays`.
- `score_points`, used by `grid_summaries` and `evaluate_shape` when `model.kind == "points"`. The selection is
  the same as for the ray decoders (best F1 at delta 0.002 over the grid), so `train.py` validates point targets
  with no change to its validation code.
- `scripts/eval_rays.py` accepts the point targets.

### Configs

`h5/configs/points_std.yaml`, `h5/configs/points_strong.yaml` (the shared defaults of `default.yaml`).

**Note on test a.** None of the 10 test shapes has a sample inside at a box end, so the boundary rule (choice 3)
was not exercised by the oracle comparison. It is covered by the synthetic test a2. The rule is exact: the
protocol's hit count equals the gate's plus the number of box ends that are inside (checked per ray in test a).

**A bug found by test a2.** The sort key of the hits was `ray * (n + 2) + (key + 1)`. The boundary exit has key
`n + 1`, which made it collide with the first key of the next ray. Hits of neighbouring rays then interleaved.
The multiplier is now `n + 3`. The test failed before the fix.

## Timing (real data, 4 workers, batch 32, N = 512)

- **`points_strong` training:** 0.105 s/it (iterations 50–300, including the data wait), peak GPU memory
  2.45 GiB, 300-iteration run in a scratch directory (not the pilot).
- **One validation** (200 shapes × 4096 rays, N = 512, both isos, decoding and scoring): **22.5 s**, measured
  after the GT cache was filled. The GT preparation of the 200 shapes is paid once per process; in H5-4 it was
  about 21 s for the same 200 shapes (not re-measured here).

## Choices (not obvious from the spec)

1. **Query points for `points_strong`.** The 1024 surface points are drawn uniformly from the stored 100 000
   points of `points_surface.npz`, so the sigma 0.002 and 0.01 halves each get about half of them. An exact split
   of 512 + 512 was not implemented.
2. **Loss scale.** The sum over 2048 points gives a loss of order 10³. Adam is approximately invariant to a constant
   scale of the loss (up to its epsilon), so the choice of scale does not matter in practice; the logged values
   are on the sum-mean scale.
3. **Boundary hits.** Choice 3 of the protocol (see above). The gate's `points_512` has no boundary hits, so any
   comparison with the gate must account for them; test a does this.
4. **Bisection steps.** `B = 8`, as specified: the bracket after 8 steps is `h_512 / 256`, about 8.4e-6, so the
   hit error is at most about 4e-6. The gate bisects to 1e-7, and the difference is far below the matching delta.
5. **Same seeding as ray targets.** The point items use `SeedSequence([seed, 2, g])` in training, the same as the ray
   items, so a resumed point run draws the same batches.

## Limits

- `PointModel` supports `points_std` and `points_strong` only. The `points_std` items contain no surface points.
- The validation of point decoders uses the 4096 fixed rays of `fixed_val_rays`, the same rays as the ray
  decoders, so F1 values are comparable across targets.
- The protocol is not differentiable and is only used for evaluation, never in the loss.

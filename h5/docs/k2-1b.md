## 1. points_rayint_a / points_rayint_b are point decoders

I found the places with grep on `POINT_TARGET`, `points_strong`, `build_point_item` and `kind`:

- `models.py`: `POINT_TARGET_NAMES` now includes the two rayint targets, and `PointModel` checks against it. A test
  checks that it equals `data.POINT_TARGETS + data.RAYINT_TARGETS`. `eval_rays.py` (`decoding_grid`, the point ray
  protocol through `model.kind`) and `train.compute_loss` work from `POINT_TARGET_NAMES`, so they treat the new targets
  as point decoders: the iso grid of points_strong and ConvONet's BCE.
- `train.py`: `ALL_TARGETS` includes `RAYINT_TARGETS`. `TrainSamples` builds rayint items with `build_rayint_item`,
  passing the config's `n_rays` as the number of sampled rays. The default is 512, which equals
  `data.RAYINT_N_RAYS`, so a real run uses the K2-1a value; the dry run uses 32. The band selection (`_select`) is
  unchanged and applies to them as to points_strong.
- `scripts/eval_rays.py`: the `--target` choices include the two targets.
- `q0_report.py`: no change needed. It reads the target from each run's `config.json` and uses `build_model` and
  `decoding_grid`.
- `configs/points_rayint_{a,b}.yaml`: only `target` and `out_dir` differ from points_strong. A test checks that every
  other key of the loaded config equals points_strong's.

New tests in `tests/test_rayint.py`, 13 in total (full h5 suite after the change: 141 passed, 12 min):
- the targets are in `ALL_TARGETS`, build a `PointModel`, have the points_strong iso grid, and have the points_strong
  config apart from the target;

## 2. Thin-share diagnostic (`h5/scripts/k2_thin_share.py`, CPU)

The script uses train shapes 0, 100, ..., 9900 (100 shapes), 20 draws each, `Generator(PCG64(SeedSequence([i, d])))`,
2048 query points per item. A point's segment is the box cut at the analytic interval ends of `tree.json` along an
axis through the point: material, gap or an outer segment, the same definition as `data.rayint_segments`.
- rayint: the axis of the ray the point was drawn from;
- points_strong: all three axes, taking the shortest of the three segments.

I checked the analytic segments against the sampler's own dexel segments on rayint points: the largest difference is
2.9e-7, which is the float32 storage. The run took 147 s; the output is `h5/results/k2/thin_share.{json,md}`.

| target | share < h | share < 4 h | items |
|---|---|---|---|
| points_strong | 0.0224 | 0.0843 | 2000 |
| points_rayint_a | 0.0334 | 0.0972 | 2000 |
| points_rayint_b | 0.0006 | 0.0045 | 2000 |

Variant a puts about 1.5 times as many points as points_strong into segments shorter than h, and about 1.15 times as
many below 4 h. The control b puts almost none there. The two measures are not identical: points_strong takes the
shortest of three axes, which favours it, while rayint uses one axis.

## 3. K2-2 chain (`h5/scripts/k2.sh`)

Written in the style of `q0.sh`: resume-safe, `set -euo pipefail`, `--dry-run`, log in `ROOT/chain.log`, root
`~/PhD/runs/k2`.

1. Train `K2_points_rayint_a` and `K2_points_rayint_b` from scratch with the Q0 settings: `train_subset=32` (seed 0,
   the same 32 shapes as Q0), `eval_on_train=true`, batch 32, `max_it` 60000, `lr_steps [[50000, 1.0e-5]]`,
   `val_every` 5000.
2. Run `q0_report.py eval --grid` on model_it5000 to model_it60000 of both runs: the 32 training shapes, all rays, the
   H5-6 diagnostics, and every iso with the band selection. The output is `ROOT/eval/{run}_it{N}_grid.json`.
3. Run `q0_report.py eval --grid` on Q0_points_strong model_it60000 of `~/PhD/runs/h5_q0`. It writes
   `h5_q0/eval/Q0_points_strong_it60000_grid.json`; no `_grid` file exists there yet, and the old Q0 eval files are
   not touched.
4. Write the report with `k2_report.py`, to `h5/results/k2`.

Estimated time: points_strong ran at 0.109 s/it in Q0 (median), so about 1.8 h per run and 3.6 h for both, plus the
evaluations. This assumes the GPU is free. With the K1-4 chain on the same GPU it will take longer.

## 4. Report (`h5/scripts/k2_report.py`)

The report goes to `h5/results/k2/report.{md,json}`. At `--final-it` (60000) it gives, for K2_points_rayint_a,
K2_points_rayint_b and the re-evaluated Q0_points_strong:
- ordinary recall at 0.002;
- weighted thin recall L/h < 1, the Q0 measure. Recomputed from the old Q0 eval file at 60000 it gives 0.2473 and
  ordinary recall 0.7224, which are the 0.247 and 0.722 of the rule;
- M, precision, decoded/GT, in band, F1;
- per-bin thin tables at 0.002 and h/2;
- the K2 runs per checkpoint;
- whether all three runs used the same training shapes (`train_subset.json`).

Rule (fixed on 24. 11.):
- **CONTINUE** if points_rayint_a has weighted thin recall >= 0.297, ordinary recall >= 0.702 and decoded/GT in
  [0.8, 1.25];
- otherwise **STOP**;
- if points_rayint_b meets the same thresholds, the report prints "lines, not the weight".

The same rule with the re-evaluated Q0_points_strong values (+0.05 / −0.02) is printed as descriptive only.
